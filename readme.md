# anm 开发需求文档

> 本文档是 anm 项目的逻辑框架与设计原则的完整同步材料，供开发者（含 AI 协作者）在动手写代码前建立一致的心智模型。文档分两部分：**第一部分「设计理念」**是目前讨论下来比较清晰、作者认同的思路方向，供实现时参考对齐，但**不是不可更改的铁律**——文档里出现的具体规则、数据字段、边界划分，很多是讨论过程中的阶段性倾向，不代表作者已经拍板定死，实现时如果发现某条写得比讨论中的原意更绝对、更具体，应该以"这是当前倾向、可协商"的心态对待，而不是当成必须遵守的规范。**第二部分「架构与规格」**是当前阶段可以据此动手的具体设计。文档末尾列出了尚未解决、故意搁置的开放问题，实现时遇到这些点不要自行拍板，应停下来与作者确认。**电子笔记本来就不该比纸笔笔记本限制更多——本文档的默认取向是尽量少设规则，只在确有必要处才设边界，任何一条规则如果读起来像是在"为了完整性"而存在、而不是解决了某个具体问题，那大概率是不必要的，应该被砍掉而不是保留。**

---

## 第一部分：设计理念

### 0. 项目是什么

anm 是一个个人笔记系统的管理器：以常驻服务 **anm-core** 为核心（供人操作的 CLI、快速写入 anw、Windows 薄壳 anm-tray-win 三个应用都经 IPC 访问它，MCP Server 内置其中供 AI agent 操作），把作者既有的"文件夹 + 文本文件"笔记库（`znote`），升级为人机共享的持久记忆层。

**一句话本质**：同一块硬盘，是人的第二记忆，也是 agent 的第一记忆。

这是一个**纯个人定制项目**，没有市场化、多用户、防御性安全等考量。设计的一切复杂度取舍，都应该以"对作者一个人是否好用"为唯一标准，拒绝任何为假想的通用场景（多租户、权限体系、企业级审计）预留的过度设计。

### 1. 背景：为什么做

- **用户侧痛点**：记笔记的动机是"怕忘"，消费笔记的动机是"要用"，两者不重合。结果是笔记大量堆积、极少被读。
- **技术侧机会**：AI agent 需要跨会话长期记忆。业界主流三条路线（知识图谱 / 向量检索 / 用户画像）如果被当作**唯一/默认**的记忆结构，各有硬伤：知识图谱强拆结构、丢失语调与未定性，个人规模维护成本高；向量检索回答"哪段最像"而非"此刻需要想起什么"，相似不等于相关；用户画像是去情境化的静态总结，服务"显得了解你"而非当下任务。**这不是对这三条路线本身的否定，而是对"只用其中一种来覆盖所有记忆需求"这个做法的否定**——知识图谱、向量检索都有各自适用的具体场景，本项目也不排除未来在某个局部场景引入它们，只是不会把某一种当作贯穿全系统的默认底座。
- **核心判断**：作者已有的笔记结构（目录 + 文本 + 标签）就是最好的记忆结构。缺的不是更好的存储，而是**消费回路**——一条让笔记在决策、执行时被真正用起来的通道。anm 做的是这条回路，不是重新发明存储或检索方式。

### 2. 笔记的价值在于消费

> 笔记的价值在于在某些场景中消费，只有消费掉的笔记才是有效笔记，否则只是一种"通过记录自我满足"。

- **消费**的定义：笔记在某个使用场景中被真正用起来。
- 消费有三种**并列、无优先级**的抽象形态，区分标准是"谁在读"和"这次读是否由一个明确需求驱动"：
  - **human fetch**：人主动查（速查、翻阅）
  - **agent fetch**：agent 取用，存在明确的取用需求（回答问题、完成任务时查笔记，也包括 agent 主动发起的检查动作，如读取 skatch 做分诊）
  - **exhibit**：agent 未经明确要求，基于当下情境判断"这条笔记此刻该被看见"而主动呈现（例：决策中主动提醒容易被遗忘的约束条件"预算仅剩 500"；自由思维中主动抛出可能引发联想的旧笔记）
- **产生**（笔记的写入/新建）与**消费**（笔记的读取/取用）是笔记生命周期两个不同的动作，常常是同一事件的两面：消费的过程本身可能催生新笔记，这种转化称为**汇流**（例：skatch 里的一句随手记录经过决策期讨论，被判定为一个思维结论，转化为 insight；自由思维场景中，讨论已有 insight/idea，可能同时催生新的 project、insight、principle、idea；也可能只是执行某件事的过程中突然意识到某条旧笔记里蕴含的道理，随手记一条 insight）。**汇流没有固定的发生场合，可以在任何时刻发生，不需要被限定在某类场景内，也不需要任何触发规则——这本质上就是自由写笔记，anm 不应该为这件事增加任何门槛或流程。** 电子化笔记相比纸笔笔记本，不应该在"何时能记什么"这件事上比纸笔限制更多。

### 3. 系统服务的对象：一个独立于笔记之外的行为循环

anm 不是"更好的存储或检索系统"，而是让作者已经在实践的、以"消费"为价值标准的笔记习惯，多一个不自作主张的执行者。

**关键澄清**：所谓"决策 → 执行 → 决策……"的循环，指的是作者理想中的**人的行为节奏**，是一个行为循环概念，不是笔记系统的内部逻辑。笔记系统辅助这个循环，但不等于这个循环、不包含这个循环的调度权。

两个思维阶段，对笔记的需求方式不同：

| 思维阶段 | 使用笔记的方式 |
|---|---|
| 决策与计划 | 把原则、历史、现状同时铺开，一次看全 |
| 执行 | 随时能找回自己当时留给自己的思路上下文 |

**执行阶段的笔记不是"项目进度追踪"**——追踪进度是企业管理的手段，本项目明确排斥。执行阶段的 working 类笔记，纯粹是作者为了辅助自己完成某件事而记的笔记，服务的是"回来接着想的时候，重新进入当时的思路"，不是"检查有没有按计划推进"。

### 4. 关于"打扰"的一点倾向（非排他性规则）

目前讨论过的所有场景例子，都是作者自己主动发起的（决策场景、自由思维场景）。这只是目前的例子恰好长这样，**不代表场景只能由人发起、不代表这是什么排他性的"唯一入口"**——未来完全可以有 AI 主动发起的场景，比如定时轮询检查、agent 主动判断"该找作者聊聊了"并发起对话。这条不是需要焊死的架构约束，是留给未来扩展的空间。

目前比较明确的一点倾向是：像 skatch 分诊、标签整理这类后台维护动作，遇到拿不准的部分，没必要专门设计一个"提醒/汇报"通道去主动推给作者——留在原地，作者下次翻到自然会看见，这样更省事，不代表"系统绝对不能主动找作者"这件事本身有什么问题。

作者也可以显式设定强时间/条件绑定的提醒（例如"晚 8 点提醒我打电话"），这类提醒就是照办即可，不需要系统额外判断"重不重要"。

### 5. 两类场景：目标、行为模式、产出三者一一对应

场景是作者主动进入的模式，不是互相包含的关系，是两种独立、性质相反的 agent 行为模式：

| | 决策场景 | 自由思维场景 |
|---|---|---|
| 目标 | 明确：生成 schedule | 无固定目标 |
| 行为模式 | 收敛：agent 提供的所有信息围绕决策与 schedule 展开 | 发散：agent 以主动 exhibit 为主要驱动方式，将发散性的旧笔记摆在作者面前引发联想 |
| 典型流程 | 结构化：简报当前执行情况（working 现状）→ 结合 problem 目录提出讨论点 → 交互复盘讨论 → 针对具体决策点自动列出相关 principle 辅助判断 → exhibit 按需插入（提醒容易被忘的约束）→ 产出 schedule | 无固定流程，围绕 exhibit 出的内容自由讨论 |
| 主产出 | schedule（计划清单） | 笔记的汇流（旧笔记升级形态、新笔记诞生：新 project / insight / principle / idea） |

**log 不作为决策场景的常态输入**。log 是几乎不主动读、仅在有明确需要时才去查的存档，不属于"决策时必看的几源之一"，不要把它塞进开场简报的固定流程里。

**exhibit 的选取逻辑因场景而异**（这是同一种抽象机制在不同场景目标下的不同表现，不是两种不同机制）：
- 决策场景中：判断依据是"这条与当前决策点相关，且可能被遗漏"，服务于收敛到一个结论
- 自由思维场景中：判断依据是"这条与当前讨论存在某种联想/呼应，可能撞出新东西"，不追求收敛
- **已知悬而未决的矛盾**：自由思维场景中，exhibit 挑得太贴合当前话题会发散不起来，起不到撞出新东西的作用；挑得太不相关又会变成对思维的打断。这个分寸无法靠理论一次定死，**必须在实现中留出可调参数**，通过实际使用体感去校准，不要在 v1 强行给出一个固定权重方案。

### 6. AI 写入的自主权原则

这一条是作者在讨论标签操作边界时明确确认过、并同意推广到全部写入对象的一条规则，适用于所有类型的写入对象（标签、正文、目录结构……），不需要为每类对象单独定制权限规则：

> **AI 自主发起的写入（没有作者明确指令时的动作），只允许"新增/低风险追加类"操作（写新笔记、追加内容、新增标签、移动笔记归档到位）；凡是涉及删除、覆盖、修改已经存在的内容，自主状态下一律不允许，唯一例外是"将已存在的标签行移动到文档开头"这个纯粹的排版整理动作，因为它不改变任何语义信息。**
>
> **一旦作者显式下达命令，AI 可以执行任何操作，包括修改、删除已有内容，没有额外限制。**

即：区分权限的不是"操作对象是什么"，而是"这个动作是否被作者明确要求"。**风险与自主程度成反比**，自主程度越高，允许的操作范围越窄。

这条原则决定了 anm-core 不需要设计一套通用的 ACL/policy 引擎（如 config.toml 里的权限声明表）——边界不靠运行时检查实现，而应靠**"没给 agent 提供对应的自主调用原语"这一事实本身来保证**。每一个允许 agent 自主调用的写入原语，都应该具体到"能做什么、不能做什么"精确写死在函数签名/接口设计里，而不是一个通用的"编辑笔记"接口外面包一层权限判断逻辑。

> **人机通道的例外（不构成对自主权的放宽）**：IPC 协议里的 `WriteNote`（整篇覆盖写入）只服务于**人**——托盘内置编辑器由作者本人编辑并显式保存。该命令**不通过 MCP 暴露**，AI agent 永远拿不到整篇覆盖的能力；同时它只接受白名单内的笔记路径。MCP 侧依然只有"新增/追加/标签整理"类工具。

### 7. 标签维护是 anm 的招牌特性

标签系统不是笔记目录结构的替代或补充，是叠加在已有目录组织之上的**第二层关联网络**，与"不重组用户笔记结构"的原则不冲突——目录组织权始终完全在作者手里，AI 动的是一个原本不存在、由 AI 使用中自然生长出来的新维度。

**长期愿景**：系统运行足够长时间后，AI 根据自己的使用会积累出大量标签，标签与标签之间通过共现关系形成一张复杂而稳定的关系网络。这张网某种程度上是 AI 使用这套记忆系统留下的"人格痕迹"的外化。

**关于这张图该长什么样，目前只有一个倾向，不是定论**：原型/早期阶段，标签图的数据结构倾向于保持简单（例如只记录"哪些标签共同出现在同一批笔记里"这类朴素关联），不预先设计类型化的关系边（如"A 是 B 的一种"这种显式语义关系）。**这不是永久禁止**——是否要引入更结构化的关系表达（包括未来某个局部场景引入知识图谱式的类型化边），留到实际用起来、发现朴素共现不够用的时候再说，不需要现在就下死结论。标签之间是否需要记录"关系强度"这类具体字段，尚未讨论过，属于开放问题，不预设。

**倾向保留的一点是可见性**：这张图最好能独立于 AI 对话之外、由 anm-core/cli 直接渲染出来查看，方便作者随时看看当前标签网络的形态，也方便手动干预（删除、合并标签）。这一点不是强制要求，但符合"人格外化"这个说法本身的意义——完全看不见的东西很难称得上是人格。

### 8. anm 代码做什么，交给 LLM 做什么

**分工标准**：任何可以用确定性规则完成的信息整理、聚合、过滤、排序、呈现，都应该在 anm-core（代码层）实现，不依赖 LLM；只有需要理解笔记"语义内容"才能做出的判断，才交给 LLM。

- **anm-core 的职责**：不需要理解笔记写的是什么意思，只需要正确读取结构化信息（路径、frontmatter、标签、时间戳）。例如：列出 working/ 下的项目、按标签筛选笔记、检查 schedule 完成状态、把 problem/ 列表摆出来、渲染标签共现面板。
- **交给 LLM 的职责**：任何需要理解笔记内容语义才能完成的判断。例如：这条 problem 和哪条 principle 相关、此刻该不该提醒预算约束、skatch 里这条该分到哪个目录、两个标签是否该被认为相关。

**设计约束**：决策场景、自由思维场景等"场景"提供的信息呈现基础（开场简报、面板数据）**必须能在完全不接 AI 的情况下工作**，即作者应该能只用 anm-cli 的面板/仪表盘，不依赖任何 AI 判断，独立完成决策与思维整理的基本流程（对标"没有笔记系统时，仍然可以在打开的文件夹界面完成决策和思维过程"这个能力基准）。AI 接入带来的价值应该是**在这套面板已摆好的材料上做人力做不到或做起来很慢的语义关联**（挑相关 principle、察觉容易忘的约束、判断笔记归属），而不是从零替代面板、把所有信息呈现都交给 AI 生成。

**判断准则**：任何一个 MCP 工具背后，都应该先问一句"这个能力有没有一个不依赖 LLM 的确定性子集，可以先在 anm-core / cli 面板里实现？"如果有，先在 anm-core 实现，MCP 工具复用同一套底层数据接口，AI 只是在这层数据之上再加一层语义判断——这样面板和 AI 工具用的是同一份事实基础，不会出现两者互相矛盾的情况。

## 第二部分：架构与规格

### 9. 分层架构

```
Layer 0  存储实体层     纯文本 + 行内标签，文件系统本身即唯一真相源
Layer 1  服务层         anm-core（常驻）：现场扫描查询 / 文件监听 / 内置 MCP（HTTP + stdio）/ IPC / （规划）定时提醒
Layer 2  应用层         anm（人：CLI/面板）· anw（快速写入）· anm-tray-win（Windows 薄壳）——全部经 IPC 访问服务
Layer 3  场景编排层     不写死在代码里，是给 agent 的"剧本"文档（延伸自现有 AGENTS.md）
```

**一核心三应用**：anm-core 是唯一长期后台运行的服务进程，三个应用都是围绕它的薄壳客户端（anm 供人操作、anw 快速写入、anm-tray-win 供 Windows 侧交互）；MCP 是 anm-core 的内置功能，不单独成应用。应用与服务的通信协议（IPC）由 anm-core 定义，服务端与客户端共用同一份协议类型。

| 层 | 稳定性 | 由谁定义 | 是否依赖 LLM |
|---|---|---|---|
| 存储 | 极稳定 | 文件系统 | 否 |
| anm-core 服务 | 稳定，慢迭代 | Rust 代码 | 否 |
| 三个应用 | 中等 | 代码 | 否 |
| 场景剧本 | 易变，随时可调 | 文档，agent 执行时调用 LLM | 是 |

**分层的核心意图**：把"稳定的、可以用确定性代码实现的东西"和"易变的、依赖模型语义判断的东西"物理分离，不要混在同一处代码/同一个工具实现里。这样场景行为可以像修改文档一样迭代，anm-core 保持薄而稳定，不需要因为"决策会议该多问一句"这种行为调整而重新编译发版。

### 10. Layer 0-1：存储与索引

- **真相源唯一性**：任何上层数据结构（索引缓存、标签图存储等）都不得成为事实的第二来源，必须可以从 Layer 0 完全重建。
- **索引默认策略：现场扫描，不预建持久索引**。个人笔记库规模（几千文件、几十 MB 文本）下，现场全文/标签扫描（类似 ripgrep）的性能大概率足够，不需要一开始就上持久缓存索引的复杂度。持久索引作为**后续按需追加的性能优化层**，只有在实测发现现场扫描确实成为瓶颈时才引入，不作为 v1 的默认架构组成部分。anm-core 服务对应用提供的查询同样每次现场扫描，不缓存。
- **默认不预置语义向量索引**：批判的是"只靠向量检索做记忆"，不是向量检索这个技术本身。所以 anm-core 索引层不默认包含它，但如果某个具体场景（比如自由思维场景挑 exhibit 候选）用起来发现需要语义相似度辅助，随时可以加，不是禁区。
- **anm-core 服务当前设想的职责**：监听文件变动、（如启用）增量维护缓存索引、执行作者显式设定的定时/条件提醒、经 IPC 服务三个应用、内置 MCP（HTTP 常驻端点 + stdio 会话）。这是目前想到的范围，不是说以后永远只能做这些——只是目前没有讨论过让服务做语义判断这件事，实现时如果要加，最好先跟作者确认一下要加的是什么、为什么加。

### 11. 标签系统规格

**识别规则**（纯语法判断，不涉及语义理解，现场扫描即可完成）：

- **文本标签行**：一行文本，去除首尾空白后，若能被完整切分为一个或多个 `@token` 形式的片段（不夹杂其他文字），则该行是"文本标签行"，行内每个 `@token` 各自算一个独立标签（作用域为整篇笔记）。
- **段落标签**：段落开头（行首，允许前导空白）出现一个或多个 `@token`，其后（同一行）还有正文 → 这些 `@token` 是该段落的"段落标签"，**仅可出现在段落开头**；分隔空白兼容全角空格（U+3000）。例：`@urgent 记得交报告` → `@urgent` 是段落标签；`感谢 @张三 的建议` → 行首无标签，不计入。
- 其他位置出现的 `@xxx`（正文行内、frontmatter 等）不作为标签声明。
- 命名空间标签（如 `@for:comfyui`）语法上兼容，但**当前阶段不设计相关功能**，留待后续需要时再定义其语义与检索方式。

**AI 对标签的操作边界**（第 6 条通用原则在标签对象上的具体实例）：

- AI 的常规内容生产能力（写笔记、**新增标签**）不受限制，属于"新增/低风险追加"，自主状态下即可执行；润色、改写已有正文属于第 6 条禁止的"修改已经存在的内容"，自主状态下一律不允许，仅在作者显式指令下执行。
- AI 面对**已经存在的标签**时，自主状态下唯一允许的操作是"将其移动到文档开头"（纯粹的位置整理，不改变标签内容与语义）。修改、删除已有标签，自主状态下一律不允许。
- 一旦作者显式下达"帮我改这个标签"一类指令，AI 可以对已有标签做任意修改，不受上述限制。
- 实现上，"移动已有标签到开头"应作为一个独立的、职责单一的原语（输入笔记路径，效果是重排已识别的标签行位置），不与"新增标签"这类内容追加操作合并成一个笼统的"标签维护"接口。

**标签图数据结构**：

- 具体存什么字段（是否需要权重、要不要区分关系类型）尚未定论，见第 15 条开放问题。原型阶段先从最简单的"标签共现"关系起步（多对多关系表即可），不预先设计成复杂结构，够用即可，不够用再加。
- 倾向提供一个独立于 AI 对话之外的可视化面板（Layer 3 cli 部分），供作者随时查看当前标签网络的形态，并可手动修剪（删除/合并标签）。

### 12. anm-core 职责边界

anm-core **不感知场景概念**（不知道"决策场景""自由思维场景"是什么），只提供数据操作原语，包括但不限于：

- 笔记 CRUD（新建、追加、读取、按第 6 条规则约束的修改/删除）
- 查询原语：按标签、按目录、按时间范围、按关键词全文/标签现场扫描
- 聚合原语：将多个来源的结构化数据组合返回（如 working 现状 + problem 列表 + 待分诊条目的组合查询），**只负责拼数据，不负责组织成一段自然语言简报**——简报文字的组织属于场景剧本/LLM 的职责
- 标签图原语：加边、查共现（具体字段设计见第 15 条开放问题）、按第 11 条规则约束的整理操作
- 每一个允许 agent 自主调用的写入类原语，其允许的操作范围应精确到位（如"仅追加""仅移动标签行位置"），不设计成通用的、需要外部权限校验才能限制范围的宽泛接口

### 13. 一核心三应用

- **anm-core（核心，常驻服务）**：确定性业务逻辑（Layer 2）作为服务进程的一部分运行，对外提供两个入口：
  - **IPC 端点**：供三个应用（anm / anw / anm-tray-win）做查询与低风险写入，协议由 anm-core 定义、服务端与客户端共用；
  - **内置 MCP**：把 anm-core 原语按"是否需要常驻在上下文里"分两类暴露给 agent——
    - **MCP resource**（对应 core memory / 常驻）：小而精、session 开始即可用，不需要专门发起查询——如个人常识性事实（设备清单、账号权限等，**默认只读，不因 AI 自主写入而变化**）、标签索引摘要、当前项目概览摘要
      - 已落地第一项：**`anm://facts` 通用事实** ← 笔记库 `.agentspace/fact.md`（人工维护、默认只读、永远以当前文件内容为准；新鲜度/失效机制见第 15 条开放问题 1，暂不做）
    - **MCP tool**（对应 archival / 按需）：需要 agent 主动发起调用才会读到——如 ref/playbook/snippet 细节查询、zdb 结构化数据查询、skatch 分诊写入、标签图加边等
- **anm（应用，人机接口）**：CLI 与未来面板/仪表盘的家，经 IPC 请求服务渲染。决策场景的开场信息（working 现状、problem 列表、待分诊条目）应该能在完全不启用 AI 的情况下，通过面板直接查看，供作者独立完成决策阅读；标签关系图的可视化面板也在此处。
- **anw（应用）**：快速把一句话写入默认 skatch.md（inbox 入口），经 IPC 请求服务追加。
- **anm-tray-win（应用）**：Windows 托盘薄壳，经 TCP 连接 anm-core 服务（跨机器时连 zmain 上的服务）；内置编辑器的文件内容读写全部经 IPC 由 anm-core 完成，薄壳不直接访问服务端文件系统。

### 14. 场景剧本层（Layer 3）

场景（决策场景 / 自由思维场景）的具体行为规范——什么时候做什么、按什么顺序调用哪些层提供的原语、什么时候该主动 exhibit——**不写死在 anm-core 内置 MCP 的工具实现代码里**，而是以类似作者已有的 `AGENTS.md`（agent 会话说明书）的形式，写成可以随时修改、不需要重新编译发版的文档/skill。

这样设计的意图：

- 场景行为可以快速迭代、由作者直接阅读和修改，不需要碰 Rust 代码
- 与作者已有的工作方式（AGENTS.md）天然衔接，是其自然延伸而非另起一套
- 复杂度集中在这份易变的文档里，anm-core 服务保持薄而稳定

### 15. 尚未解决的开放问题（实现中遇到，先停下确认，不要自行决定）

1. **常识性事实的新鲜度/失效机制**：SSH 设备信息、账号密码、显卡型号、CUDA 版本等"决定行动前提"的事实，一旦过时可能导致 AI 给出错误判断（比模糊的资产类笔记过时风险更高）。需要一套"这条事实上次确认时间、是否需要显式标记过期"的机制，具体设计尚未展开。
2. **跨 session 的短期接续（recall 粒度）**：多设备共享同一份 znote，宏观语境一致（场景已验证），但"我们上次谈到哪、接下来该干什么"这种更细颗粒度的短期连续性，笔记文件本身不天然携带，是否需要、需要到什么程度，尚未讨论。
3. **自由思维场景 exhibit 的相关性/意外性配比**：第 5 条已述的矛盾（太相关发散不起来，太不相关变打断），需要留可调参数，具体调节机制、默认值、是否需要作者手动反馈校准，尚未设计。
4. **决策场景以外，是否需要以及如何设计更多场景类型**：目前只明确了决策场景与自由思维场景两种，是否存在第三种典型场景，暂未讨论，不要提前假设或扩展。
5. **分诊（triage）机制的具体触发方式**：场景三示例中"AI 在空闲时整理 skatch"，具体是 anm-core 服务检测文件变动后自动唤起，还是完全由作者手动触发（或作为进入决策场景时的"会前准备"步骤之一自动执行），倾向于后者（作为决策场景的会前准备），但尚未最终拍板，实现前需确认。
6. **命名空间标签**（如 `@for:comfyui`）的语义与检索设计，当前明确搁置，不在 v1 范围内。
7. **标签图的具体数据结构**：是否需要记录关系强度/权重、要不要在某些场景引入类型化的关系边，都还没讨论过，不要在实现时替作者预先决定，动手前先问。

### 16. Windows 薄壳（定位保留）

Windows 侧（托盘程序 anm-tray-win、全局快捷键呼出的交互窗口等）**仅为薄壳**：主要功能全部运行于 Linux / WSL，Windows 侧需要与笔记系统交互时经 **TCP** 连接 WSL 内的 anm-core 服务。架构上托盘按"**跨平台共享核心（anm-tray-core）+ 平台外壳（anm-tray-win，未来 anm-tray-wayland / anm-tray-android）**"分层，逻辑可复用。已实现并验收：

- **单例常驻**；全局快捷键（默认 **`Alt+Shift+Z`**，可在托盘菜单「设置快捷键…」里按新组合重新设置并持久化）呼出/隐藏覆盖层——**可见状态下再按一次即取消激活（切换语义）**；
- 覆盖层：全屏**半透明变暗**（背景透出但整体压暗，卡片纯色不透明），屏幕中央不透明输入框（**anw 语义：回车即写入 skatch.md**；支持**斜杠命令** `/help` `/find` `/search` `/tags` `/ls` `/inbox|/anw` `/open`，与 anm 命令一致），一级目录卡片环绕展示（含**子目录行**，点击生成**临时子卡片**，取消激活不保留；临时子卡片与主卡片同配色）；
- 覆盖层**右上角状态栏**：连接状态（绿=最近一次 IPC 成功 / 红=失败）+ 当前服务地址 + 当前快捷键；
- 点击目录/文件用系统默认方式打开（`SEE_MASK_FLAG_NO_UI`：服务端路径在本机打不开时**不弹系统错误框**，改为轻提示 toast），**文本文件用内置临时编辑器**打开（多行编辑、滚动、Ctrl+S 保存、Esc 退出自动保存、**文件名可改**（同目录重命名，`RenameNote` IPC）、「打开所在位置」按钮）——**内容读写全部经 IPC（`ReadNote` / `WriteNote`）由 anm-core 完成**，因此**跨机器也能编辑服务端笔记**，薄壳不直接访问服务端文件系统；编辑器布局：上/下两条**贯通分割线**把头部（文件名输入框）、编辑区、功能区（完整路径 + 按钮）分开；
- **轻提示（toast）**：右上角小窗自动隐藏（设置生效、快捷键更新、打开失败等场景）；
- 卡片：**标题栏**（文件夹名，上下收窄、内容垂直居中于边框与分隔线之间）、**贯通分隔线**、行悬停为**左右贯通阴影条**、卡片右上角**「+」新建按钮**（位置固定，滚动后仍可见；点击进入新建模式：输入框预填目录、回车创建 `CreateNote`、Esc 取消）；**按住可拖动卡片、位置自动记忆**（`%APPDATA%/anm-tray-win/layout.json`），**滚动位置跨激活记忆**；卡片行数超出可**滚轮滚动**（细滚动条，起点在标题分隔线之下）；点击空白取消激活；点击/拖动卡片**不抢输入框焦点**；
- 托盘右键菜单：「**显示**」「设置服务地址…」「**设置快捷键…**」「退出」；「设置服务地址…」对话框可填**主机:端口**与**访问令牌**（可选，与服务端 `[server] token` 一致），持久化到 `%APPDATA%/anm-tray-win/config.json`，支持跨机连接（如 anm-core 跑在 zmain 时填 `192.168.0.102:17370`）。跨机访问要求 anm-core 的 `[server]` 绑定 `0.0.0.0`。

Windows 薄壳不改变服务的职责划分——anm-core 仍只做监听、IPC、MCP 与显式提醒，不因此承担任何语义判断类职责。交叉编译方法见 feature.md「构建与交叉编译」。

### 17. 访问安全（现状与规划）

面向"未来手机 / 远程访问 zmain 上的 anm-core"提前定下的边界与措施：

**现状（已落地）**
- `[server] token`：可选访问令牌。配置后所有 IPC 请求必须携带相同令牌（`Envelope.token`），否则拒绝；未配置时放行（局域网默认宽松）。令牌比较为常数时间实现。
- 客户端令牌来源：托盘「设置服务地址…」对话框 / 环境变量 `ANM_SERVER_TOKEN`；CLI 读配置 `[server].token`。
- 所有写路径（含 `WriteNote`）一律过路径白名单（笔记库根目录内、防目录穿越/符号链接逃逸），`WriteNote` 只走人机通道，MCP 不暴露。
- 地址/令牌均不可从不可信输入注入（`validate_addr` 拒绝非 ASCII 字符）。

**规划（实现前确认，不自作主张）**
- **公网暴露的底线**：不直接裸奔端口。手机访问优先走 **Tailscale / WireGuard 内网穿透**或 **SSH 隧道**，anm-core 仍只监听内网地址；实在要直连公网时，再加一层 TLS + 令牌（当前令牌明文传输，仅适合内网）。
- MCP HTTP 端点默认只绑回环（127.0.0.1），远程 agent 会话经 SSH 隧道复用；不单独对公网开放。
- 若未来需要更细的写入限制（如只读令牌、按应用区分权限），在协议层加**令牌类型**字段，不引入通用 ACL 引擎（与第 6 条一致）。
